ghcr.io/oubay-s/fintech-<service-name>:<git-sha>

- **Image prefix:** `fintech-`

  - `:<short-sha>` for reproducible CI builds

## 3. Financial Scale, Balances & Invariants (PaySim Aligned)

In accordance with Section 11 of Conception Plan V2.3, all money amounts operate at **PaySim magnitudes**:

- **Currency:** Simulated PaySim currency units.
- **Initial Balances (`app.wallet.initial-balance`):**
  - **Regular Customers:** `1,000,000.00` credited upon registration via `TOPUP` ledger entry.
  - **Cash Agents (`accountKind = AGENT`):** `0.00` initial balance.
- **Transfer Limits (`app.transfer.max-amount`):** `10,000,000.00`.
- **Near-Drain Ratio Threshold (`risk.policy.review-balance-ratio`):** Default `0.8` (ratio of $\text{amount} \div \text{sender\_old\_balance} \ge 0.8$ triggers near-drain rule R5 review).
- **Core Operations:**
  - `TRANSFER`: Customer to customer.
  - `CASH_OUT`: Customer to Cash Agent (`accountKind = AGENT`). Both are **core MUST** operations.
- **Financial Invariants (Zero Money Creation/Loss):**
  - **I1:** `wallet.balance` = $\sum(\text{TOPUP} + \text{CREDIT} - \text{DEBIT})$
  - **I2:** `wallet.held_amount` = $\sum(\text{HOLD} - \text{RELEASE})$
  - **I3:** Total system balances equal total admin top-ups: $\sum \text{balances} = \sum \text{TOPUPs}$.
  - Verification endpoint: `GET /admin/ledger/verify` (called after chaos tests and integration runs).

## 4. Frozen ML Inference Contract (`POST /predict`)

The ML inference contract between `risk-service` and `ml-serving` is **100% frozen** (Section 17 & 24.3):

### Request (`POST /predict`):
Risk Service sends a structured payload with `schema_version`, `request_id`, and `features` containing **strictly these 6 PaySim fields**:
```json
{
  "schema_version": "1.0",
  "request_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "features": {
    "type": "TRANSFER",
    "amount": 1000.00,
    "sender_old_balance": 5000.00,
    "sender_new_balance": 4000.00,
    "receiver_old_balance": 200.00,
    "receiver_new_balance": 1200.00
  }
}
```
*Note:*
- `request_id` is a UUID generated by Risk (echoed unchanged in the response so Risk can correlate responses to calls and logs across services).
- All derived features (drain ratio, zero balance after, amount equals old balance) are computed **internally by ML Serving**. Risk never sends more than these 6 fields.
- `*_new_balance` values are **computed by the application** as expected post-transfer balances prior to execution.

### Response (`POST /predict`):
```json
{
  "schema_version": "1.0",
  "request_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "action": "HUMAN_REVIEW",
  "fraud_probability": 0.0132,
  "uncertainty": {
    "method": "split_conformal",
    "confidence_level": 0.95,
    "prediction_set": ["legit"],
    "score": 0.08
  },
  "model": {
    "name": "fraud-detector",
    "version": "1.0",
    "stage": "Production"
  },
  "explanations": [
    { "feature": "amount", "contribution": 0.31 }
  ],
  "inference_ms": 7.4
}
```
- **Contract Schema Details:**
  - `schema_version`: String (`"1.0"`) included in every request/response.
  - `request_id`: Echoed unchanged from the request.
  - `action`: Advisory suggestion only (`ALLOW`, `BLOCK`, `HUMAN_REVIEW`). The Risk service owns the final decision.
  - `uncertainty`: Conformal prediction object containing `method`, `confidence_level`, `prediction_set` ($\subseteq \{\text{legit}, \text{fraud}\}$), and scalar `score` $\in [0, 1]$ for dashboards and alerts.
  - `model`: Metadata object identifying model `name` (strictly `fraud-detector`), `version`, and `stage`.
  - `explanations`: Optional list of `{ feature, contribution }` computed cheaply (top 3 features from native model attributions). Model-agnostic SHAP per request is strictly forbidden as it violates the 300 ms latency budget.
- **Performance & Resilience Budget:**
  - p95 inference latency **< 300 ms** at target concurrency.
  - Risk $\to$ ML client configuration: `connectTimeout = 500ms`, `readTimeout = 1500ms`, 1 retry on connect error or 5xx, max total budget 1.5s.
- **Model Types:** ML model is trained on all 5 PaySim types (`TRANSFER`, `CASH_OUT`, `PAYMENT`, `CASH_IN`, `DEBIT`), but production application traffic only generates `TRANSFER` and `CASH_OUT`. Other types never reach `/predict` (guarded by rule R1b).

## 5. Risk Decision Policy (Rules R1 – R6)

The Risk Service owns the final binding decision; ML `action` is a suggestion only. Rules are evaluated in strict order (first match wins):

| Rule | Condition | Decision | Reason Code / Tag |
|---|---|---|---|
| **R1** | Sender or receiver wallet owner is not `ACTIVE` (or self-transfer) | `REJECTED` | `ACCOUNT_RESTRICTED` |
| **R1b**| Transaction type is not supported by application (defensive, no ML call) AND `amount ÷ sender_old_balance ≥ risk.policy.review-balance-ratio` | `PENDING_REVIEW` | `BALANCE_RATIO_HIGH` |
| **R1b**| Transaction type is not supported by application (defensive, no ML call) | `APPROVED` | `TYPE_NOT_SCORED` |
| **R2** | ML service unavailable, timeout (> 1500 ms / retry exhausted), circuit breaker open, or invalid response | `PENDING_REVIEW` (`degraded=true`) | `SERVICE_DEGRADED` |
| **R3** | Model prediction set is `{fraud}` | `REJECTED` | `MODEL_HIGH_RISK` |
| **R4** | Model prediction set is uncertain (`{legit, fraud}` or `{}`) | `PENDING_REVIEW` | `MODEL_UNCERTAIN` |
| **R5** | Model `{legit}` BUT near-drain ratio `amount ÷ sender_old_balance ≥ risk.policy.review-balance-ratio` (default `0.8`) | `PENDING_REVIEW` | `BALANCE_RATIO_HIGH` |
| **R6** | Model `{legit}` AND balance ratio `< risk.policy.review-balance-ratio` | `APPROVED` | `none` |

> **Near-Drain Rule (R5) Notes:**
> - Catches transfers where the model is confident the transaction is legitimate, but the transfer drains a large share of the sender's balance (`amount ÷ sender_old_balance ≥ risk.policy.review-balance-ratio`, default `0.8`).
> - A full 100% balance drain is typically caught by R3 (`MODEL_HIGH_RISK`), while uncertain cases go to R4 (`MODEL_UNCERTAIN`). R5 specifically catches transfers of roughly 80–99% of the balance that the model approves.
> - R5 is **rule-driven, not model-driven**, ensuring analyst queue activity even when the ML model is highly sharp.
> - The ratio uses the same `sender_old_balance` sent to ML Serving (no extra calls needed).
> - The property is configurable; if unset, R5 is disabled.

## 6. Observability, Metrics & Alerts

All services must expose standard Prometheus metrics. Custom business metrics are a binding contract with Grafana dashboards:

### Key Metrics:
- `fintech_transfers_total`: Counter tagged by `status`, `reason`.
- `fintech_payment_requests_total`: Counter tagged by `status`.
- `fintech_decisions_total`: Counter with tags `decision` (`APPROVED`, `REJECTED`, `PENDING_REVIEW`), `reason` (`ACCOUNT_RESTRICTED`, `BALANCE_RATIO_HIGH`, `TYPE_NOT_SCORED`, `SERVICE_DEGRADED`, `MODEL_HIGH_RISK`, `MODEL_UNCERTAIN`, `none`), `degraded` (`true`/`false`), `scored` (`true`/`false`).
- `fintech_ml_call_seconds`: Timer measuring ML call latencies (`outcome`).
- `fintech_review_cases_open`: Gauge tagged by `priority`.
- `fintech_review_case_oldest_age_seconds`: Gauge tracking review backlog age.
- `fintech_review_decisions_total`: Counter tagged by `resolution`.
- `fintech_wallet_lock_wait_seconds`: Timer measuring optimistic/pessimistic lock contention.
- `fintech_outbox_pending` / `fintech_outbox_delivery_failures_total`: Outbox health monitoring.

### Rejection & Policy Reason Codes:
- **Risk Decision Reasons (`reason`):** `ACCOUNT_RESTRICTED`, `BALANCE_RATIO_HIGH`, `TYPE_NOT_SCORED`, `SERVICE_DEGRADED`, `MODEL_HIGH_RISK`, `MODEL_UNCERTAIN`, `none`.
- **Transaction Rejection Reasons (`rejection_reason`):** `RISK_POLICY`, `ANALYST_DECISION`, `REVIEW_EXPIRED`, `INSUFFICIENT_FUNDS`, `ACCOUNT_RESTRICTED`, `SYSTEM_ERROR`.

### Derived PromQL Signals (DevOps Alerting):
- **Uncertainty Ratio (ML Uncertainty High Alert):** Calculated strictly on `reason="MODEL_UNCERTAIN"` over all scored decisions (excluding `BALANCE_RATIO_HIGH` and `SERVICE_DEGRADED`):
  ```promql
  sum(rate(fintech_decisions_total{reason="MODEL_UNCERTAIN"}[5m]))
  /
  sum(rate(fintech_decisions_total{scored="true"}[5m])) > 0.25
  ```
- **Degraded Ratio:** Ratio of `reason="SERVICE_DEGRADED"` over total decisions.
- **Review Queue Backlog:** Monitored via `fintech_review_case_oldest_age_seconds` and `fintech_review_cases_open`.

## 7. Health Checks & Kubernetes Probes

Every service must provide health endpoints adhering to Kubernetes lifecycle requirements:

### Spring Boot Services (Roles 1 & 2):
- **Startup Probe:** `/actuator/health/liveness` with `failureThreshold: 30`, `periodSeconds: 2` (tolerates 30–60s cold start).
- **Liveness Probe:** `/actuator/health/liveness` (`periodSeconds: 10`).
- **Readiness Probe:** `/actuator/health/readiness` (must check DB connectivity ONLY, never downstream microservices).
- **Metrics:** `GET /actuator/prometheus`.

### FastAPI Model Serving (Role 5):
- **Liveness:** `GET /health/live` (process is responsive).
- **Readiness:** `GET /health/ready` (returns `200 OK` **strictly after the model is loaded into memory**).
- **Metadata & Viz:** `GET /model-info` and `GET /viz/{pca|tsne|umap}`.
- **Metrics:** `GET /metrics`.

## 8. Deterministic Triggers for Demos and E2E Tests

To ensure automated Playwright E2E tests and live demonstrations are 100% reproducible:
- **`APPROVED` trigger:** A partial transfer with amount well below 80% of sender's balance (`amount ÷ sender_old_balance < 0.8`) to a known receiver.
- **`REJECTED` trigger:** A transfer of the **entire balance** to a new receiver (*drain pattern*, triggers `MODEL_HIGH_RISK` via R3).
- **`PENDING_REVIEW` trigger:**
  - *Rule-driven (Near-Drain):* A transfer taking $\ge 80\%$ (e.g. ~85%) of sender's balance that the model approves (`BALANCE_RATIO_HIGH`, R5).
  - *Resilience-driven:* Any transfer executed while the ML service/stub is stopped (`SERVICE_DEGRADED`, R2).

## 9. Git & Pull Request Workflow

- **Branch Protection on `main`:** Direct push disabled, 1 peer review required, `CI Quality Gate Status` check required and passing.
- **Branch Naming Standard:** `feat/<role>-<topic>` (e.g., `feat/role1-auth-jwt`, `feat/role4-paysim-eda`).
- **Conventional Commits:** `feat`, `fix`, `ci`, `docs`, `test`, `refactor`, `chore`.
- **Automated Issue Closure:** Include `Closes #<issue_id>` in the PR description.
